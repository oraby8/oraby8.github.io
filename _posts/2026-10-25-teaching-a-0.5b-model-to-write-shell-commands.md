I built **shellsafe**, a tool that turns a plain-English request into one Bash command, explains each flag, rates how risky the command is, and can show its real output from a sandbox. The model behind it has 0.5 billion parameters and runs on a laptop CPU. On the NL2SH-ALFA benchmark it scores 53.7%, up from 25.3% for the model I started from and 4 points short of the 30B model that taught it.

```
$ shellsafe ask "list all python files in this folder sorted by size"
╭─ best ─────────────────────────────────────────────────────────╮
│ find . -name '*.py' -exec du -h {} \; | sort -hr               │
│                                                                │
│ ● safe                                                         │
│                                                                │
│   sort -h  compare human readable numbers (e.g., 2K 1G)        │
│   sort -r  reverse the result of comparisons                   │
╰────────────────────────────────────────────────────────────────╯
```

The model and its training data are public: [shellsafe-qwen2.5-coder-0.5b](https://huggingface.co/ahmedsamirtarjama/shellsafe-qwen2.5-coder-0.5b) and [shellsafe-bash-sft](https://huggingface.co/datasets/ahmedsamirtarjama/shellsafe-bash-sft). This post is what I tried, what failed, and the few things that moved the number.

## Why it had to be small

I set two hard rules: under 1B parameters, and CPU only. A command helper lives in your terminal, so it should answer in about a second, work offline, and never send your file names to an API.

Those rules took the easy fix off the table. Every gain had to come from data, training and how the answers are picked. I started from Qwen2.5-Coder-0.5B-Instruct, and the shipped model is a 507 MB Q8\_0 GGUF file.

## Measuring it, and finding the ceiling

Every number here comes from the 300-task test split of [NL2SH-ALFA](https://huggingface.co/datasets/westenfelder/NL2SH-ALFA), scored with the InterCode-ALFA harness. Each predicted command runs in a Docker container, and an LLM judge (qwen3.8 on Ollama) decides whether it did what the reference command does.

Two things changed my plans early:

- **The judge was not repeatable.** It flipped about 2% of its verdicts between runs, which is the size of many of my changes. I fixed its temperature and seed and cached every verdict, so the same command always gets the same score.
- **The goal was wrong.** I started out aiming for 70%. Then I ran my planned teacher, Qwen3-Coder-30B-A3B-Instruct, through the same harness: 57.7%. A 0.5B student was not going to beat a 30B teacher by 12 points on the same judge, so I reset the target to 52–55%.

The ceiling check was cheap, and it changed what a good result meant.

## What didn't work

A plain fine-tune (v2: tldr pages, the NL2SH-ALFA train split and teacher-written pairs, all checked in a sandbox) reached 44.3%. Everything I tried on top of it landed between 41% and 46%:

| Idea | Result | Why it fell short |
| --- | --- | --- |
| Put retrieved tldr docs and similar examples in the prompt | 38.7%, vs 46.3% without | The model learned to copy from the docs, and retrieval found the right page only about 70% of the time |
| DPO: working answers preferred over broken ones | 43.3–45.0% | Only about 17 of 300 test answers were broken in the first place |
| DPO with pairs ranked by the judge | 41.0–43.3% | The model drifted toward long, odd commands |
| GRPO with a sandbox + judge reward | 45.0% | Training reward rose from 0.45 to 0.52; the benchmark barely moved |
| Extra fine-tuning on hard cases | 44.7% | Within noise of v2 |

The error analysis explained it. Most wrong answers ran fine but did something slightly different from what was asked. Preference training on broken versus working commands can't fix that, and v2 and the 30B teacher both missed the same 100 questions.

## What worked: data aimed at the model's own mistakes

The first real gain came from new data aimed at the error types in v2's failures: reading file contents, absolute paths, complex `find` filters, flags that avoid interactive prompts, multi-step pipelines, and the current folder versus home.

The local 30B teacher did the work, in four steps:

1. It wrote requests about a fixed fixture file system: a home folder, `/testbed`, `/system` and `/workspace`, each holding known files. Each call got 5 random files and 4 random operations, so the requests didn't all look alike.
2. It answered each request with a command.
3. In a separate call, without seeing that command, it answered the same request again.
4. Both commands ran in the sandbox. A pair was kept only when they printed the same non-empty output. Empty output counted only for commands that change files, and only when the two commands agreed.

Any request too close to a test question (word overlap of 0.6 or more) was dropped. That left 11k pairs. Retraining from the base model on the v2 mix plus these pairs gave **v4: 50.7%**. Against v2 it gained 35 questions and lost 16.

It also picked up a new habit. The teacher's requests often named home files as `~/notes.txt`, so v4 started adding `~/` where the request just said `notes.txt`. The next round listed files by bare name and dropped `~/` from half the rows, and the habit went from 7 cases to 2. That round had 16.7k pairs and more hard pipelines, yet **v5 scored 49.7%**, no better than v4. More of the same data didn't add more.

## Three more points without more training

The last points came from how answers are picked, not from training.

**Weight averaging.** v4 and v5 got about the same score but got different questions right. Averaging their weights into one model (v45) scored 50.0% on its own.

**A vote over real outputs.** For each request the model writes one greedy answer and 5 samples at temperature 0.7. Every one rated safe runs in the sandbox, and answers that print the same output count as the same answer. The biggest group wins, and ties go to the greedy answer. This took v45 to **53.0%**: 11 questions gained, 2 lost.

**A fallback instead of a repair loop.** I wanted a multi-turn loop: run the command, show the model its error, let it try again. I measured whether the sandbox could even tell a wrong answer first. It mostly couldn't. Of 141 wrong answers, 46% showed an error or empty output, but so did 43% of the 159 right ones. The sandbox is not the test machine, so a missing file or no network often meant nothing. Only three errors were a real sign: a bad flag, a missing tool, or a syntax error, seen in 9 wrong answers and 1 right one.

So instead of a loop, a winner that fails with one of those three drops behind the next answer that ran cleanly. That changed 7 answers, fixed 2 and broke none: **53.7%**.

| Step | Accuracy | Easy | Medium | Hard |
| --- | --- | --- | --- | --- |
| Qwen2.5-Coder-0.5B-Instruct (base, zero-shot) | 25.3% | 0.47 | 0.17 | 0.13 |
| v2 (plain SFT: tldr + NL2SH train + teacher pairs) | 44.3% | 0.58 | 0.38 | 0.37 |
| v4 (+ 11k targeted fixture-verified pairs) | 50.7% | 0.59 | 0.53 | 0.40 |
| v5 (+ 16.7k targeted pairs, bare file names) | 49.7% | 0.67 | 0.46 | 0.36 |
| v45 (v4 + v5 weight average, greedy) | 50.0% | 0.64 | 0.48 | 0.38 |
| v45 + sandbox output vote | 53.0% | 0.70 | 0.50 | 0.39 |
| **v45 + sandbox output vote + fallback (shellsafe CLI)** | **53.7%** | **0.70** | **0.51** | **0.40** |
| *Qwen3-Coder-30B-A3B-Instruct (teacher ceiling)* | *57.7%* | *0.76* | *0.54* | *0.43* |

*(NL2SH-ALFA test set, 300 tasks · InterCode-ALFA harness, cached qwen3.8 judge)*

The plain fine-tune was the biggest single jump. Targeted data then added 6.4 points, and picking answers by their sandbox output added 3 more.

## Turning a model into a tool

The model only writes commands. Everything around it is plain code you can read and test:

- **Safety rating.** Rules rate each command safe, caution or dangerous and say why. Only commands rated safe ever run, and only in the sandbox.
- **Sandbox.** A throwaway Docker container with no network, no capabilities, 256 MB of memory and a timeout. Your current folder is mounted read-only, so commands see your real files but can't change them. `--try` shows the best command's actual output.
- **Flag explanations.** Each flag is explained from the man page or tldr. A flag that no doc mentions gets a warning that it may not exist, and a tool that isn't installed gets one too.
- **New tools.** `shellsafe learn <tool>` indexes a tool's `--help` output, man page or README, for tools tldr doesn't cover.
- **Speed.** A cold call takes about 5 seconds, most of it loading the model. An optional daemon keeps the model in memory: 1.4 s per call with the vote, 0.6 s with `--fast`. It never starts by itself. You turn it on with `shellsafe daemon start` and off with `stop`.

Commands are never run on your machine, only shown.

```
request
  │
  ▼
1. Generate 6 candidates     1 greedy (T=0) + 5 sampled (T=0.7) from the 0.5B GGUF
  │
  ▼
2. Rate safety               deterministic rules → safe / caution / dangerous
  │
  ▼
3. Run safe candidates       one read-only Docker container (--network none, cwd mounted :ro)
  │
  ▼
4. Vote by output            candidates that print the same stdout group together; ties go to greedy
  │
  ▼
5. Fallback check            if the winner fails with a bad flag, missing tool, or syntax error,
  │                          promote the next candidate that ran cleanly
  ▼
6. Explain & display         man / tldr flag descriptions + warnings for unknown flags or missing tools
```

Answers that aren't rated safe never run; they still vote, matched by their text.

## How it compares with other small models

Every other small model I tested, run through the same harness and judge, scored at least 7 points lower.

| Model | Params | Accuracy |
| --- | --- | --- |
| **shellsafe (0.5B + sandbox vote + fallback)** | **0.5B** | **53.7%** |
| **shellsafe model alone, greedy** | **0.5B** | **50.0%** |
| kitty-bash-llm | 0.5B | 46.0% |
| shellminator-qwen05b-dpo-selfplay | 0.5B | 43.0% |
| nl-to-bash (NL2SH-ALFA train) | 0.5B | 40.3% |
| Qwen2.5-Coder-0.5B-Instruct (8-shot) | 0.5B | 28.0% |
| Qwen2.5-Coder-0.5B-Instruct (zero-shot) | 0.5B | 25.3% |
| Qwen3.5-0.8B | 0.8B | 23.0% |
| Qwen2.5-Coder-0.5B-Instruct-NL2SH (paper authors) | 0.5B | 22.3% |
| Qwen3-0.6B | 0.6B | 11.3% |
| SmolLCoder-360M-Instruct | 360M | 10.3% |
| functiongemma-270m-it (chat / tool-calling) | 270M | 0–0.7% |
| KLM-1.5 (8-shot) | 99M | 0.0% |

*(NL2SH-ALFA test set, 300 tasks · same harness and cached judge for every model)*

The low scores aren't parsing bugs; I read the raw outputs. SmolLCoder often repeats the request back. functiongemma refuses with a normal prompt, and in its function-calling mode it invents commands like `copy a b`. KLM-1.5 is a 99M base model, and it writes text shaped like commands (`list --list`). Two more models I looked at couldn't be scored: one is a speculative-decoding draft model that can't answer on its own, and the other is a steering vector for a model over 1B.

## What I'd tell myself at the start

1. **Find the ceiling first.** Run the strongest model you can through your exact benchmark before you set a goal.
2. **Make the scorer repeatable.** A judge that flips 2% of verdicts hides every change smaller than that.
3. **Read the failures before picking a method.** Mine ran fine but answered the wrong question. No training trick fixes that; data aimed at those mistakes did.
4. **Let execution check the data.** Two blind teacher answers that print the same output are a cheap and strict filter.
5. **Measure an idea's upside before you build it.** One short analysis turned a planned multi-turn repair loop into a small, safe fallback.

## Limits

- About 60% of the hardest multi-step requests still get a wrong command, often one that runs but does something slightly different. Read a command before you run it.
- It targets GNU/Linux Bash. macOS and BSD flags can differ.
- English only.

```bash
git clone https://github.com/oraby8/shellsafe.git shellsafe && cd shellsafe
scripts/setup.sh
.venv/bin/shellsafe ask "find files changed in the last day"
```
